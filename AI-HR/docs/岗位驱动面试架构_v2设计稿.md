# 岗位驱动面试架构 v2 设计稿

适配现有 AI-HR 代码的迁移方案

## 1. 文档目标

- 本设计稿用于把现有 AI 面试系统从“题目驱动 + 阶段驱动”升级为“岗位驱动 + 能力证据驱动”。
- 目标不是推翻现有代码，而是在复用现有 `ai_interviews.py`、`question_flow.py`、`flow_policy.py`、`prompt_builder.py` 的基础上，逐步引入岗位策略、能力模型、证据状态和动态调度能力。
- 首批重点支持计算机技术岗位，包括后端、前端、全栈、AI 应用、测试、运维/SRE 等岗位。

## 2. 现有系统问题总结

- 当前流程已经具备阶段感、题库、追问、风控和报告能力，但整体仍偏“技术栈核验型面试机”。
- 不同岗位的考察差异没有被抽象为稳定的岗位策略，更多只是题目文本和技能词的变化。
- 追问逻辑仍然偏“补细节/补长度/补量化”，而不是围绕能力证据缺口做方向性深挖。
- 题目生成、追问、评分之间缺少统一的岗位能力模型，导致生成和判断偶尔割裂。
- 阶段配额目前明显偏向 `S3` 技术栈核验，不完全适合 AI 应用、测试、运维、平台等岗位。

## 3. v2 设计原则

- 统一主引擎，不同岗位加载不同策略。
- 岗位驱动的核心不是换题，而是换能力模型、证据计划、流程权重和评分策略。
- 题目、追问、评分都围绕 `competency` 和 `evidence` 运转，而不是只围绕 `question` 文本运转。
- 配置优先，代码兜底，新岗位尽量通过配置扩展。
- 迁移优先复用既有链路，对外接口尽量稳定。

## 4. v2 总体架构

建议拆成六层：

1. `Role Profiler`
2. `Role Strategy Registry`
3. `Interview Planner`
4. `Evidence State Engine`
5. `Followup Selector`
6. `Report Synthesizer`

职责说明：

- `Role Profiler` 负责把岗位标题、JD、技能归一化为稳定的 `role_family`。
- `Role Strategy Registry` 负责按 `role_family` 加载岗位策略配置。
- `Interview Planner` 负责根据岗位策略、简历、JD、技能生成一份 `InterviewPlan`。
- `Evidence State Engine` 负责每轮回答后更新能力证据覆盖状态。
- `Followup Selector` 负责判断继续追问、转场、降难、切项目线程还是结束。
- `Report Synthesizer` 负责按能力证据而不是按题目列表生成最终报告。

## 5. 岗位驱动的五个核心对象

- `role_profile`：岗位画像，定义 stage 权重、能力模型、追问策略、题目生成策略。
- `competency_model`：岗位能力模型，如 `ownership`、`troubleshooting`、`rag_pipeline`、`test_design`。
- `evidence_plan`：每个能力项要求的证据集合，如 `personal_ownership`、`tradeoff`、`metric_result`。
- `flow_policy`：面试流程策略，包括阶段权重、是否需要 anchor project、最大追问数等。
- `scoring_policy`：评分权重和证据等级映射。

## 6. 角色分类方案

- 建议先把自由文本岗位标题和 JD 归一化到 `role_family`，而不是直接按 `title` 判断。
- 首批建议支持：
  - `backend_engineer`
  - `frontend_engineer`
  - `fullstack_engineer`
  - `ai_application_engineer`
  - `qa_engineer`
  - `sre_devops_platform`
- `Role Profiler` 建议采用“规则优先 + LLM 辅助 + 人工可覆盖”的方案。
- `Role Profiler` 的输出建议写入 session payload，包括：
  - `role_family`
  - `role_profile_version`
  - `seniority_guess`

## 8. 证据模型方案

- 每个 `competency` 不直接靠“回答像不像”判断，而是拆成 `required_evidence`。
- 例如 `db_cache_mq` 可拆为：
  - `real_usage_context`
  - `architecture_position`
  - `selection_reason`
  - `tradeoff`
  - `failure_handling`
- 例如 `troubleshooting` 可拆为：
  - `signal_selection`
  - `narrowing_strategy`
  - `root_cause_reasoning`
  - `validation_step`
- 建议 evidence 状态统一为：
  - `missing`
  - `weak`
  - `partial`
  - `strong`
- 每轮对话后更新 `evidence_state`，而不是只更新 `active_question_index`。

## 9. 追问轴设计

- 建议把追问标准化为 `followup_axis`，而不是自由发挥。
- 首批统一追问轴建议包括：
  - `ownership_probe`
  - `mechanism_probe`
  - `decision_probe`
  - `tradeoff_probe`
  - `evidence_probe`
  - `failure_probe`
  - `scope_probe`
- 不同岗位可以配置默认优先级，例如：
  - AI 应用更重 `decision/eval/tradeoff`
  - SRE 更重 `signal/failure/recovery`
- `Followup Selector` 的职责是选择“下一步要问哪一类追问”，而不是直接拼接最终问题文本。

## 10. InterviewPlan 设计

- `InterviewPlan` 是会前生成的面试计划，不只是题单。
- 它至少包含：
  - `role_family`
  - `language`
  - `anchor_projects`
  - `competency_targets`
  - `stage_plan`
  - `planned_questions`
- `planned_questions` 建议包含：
  - `question_id`
  - `stage`
  - `competency_id`
  - `question`
  - `target_evidence`
  - `followup_axes`
  - `max_followups`
  - `anchor_project_id`
- 现有 `question_pack` 可以逐步升级为 `InterviewPlan` 的简化视图。

## 11. InterviewEvidenceState 设计

- 运行时建议维护 `InterviewEvidenceState`，而不是只维护 `question_statuses` 和 `followup_count_current`。
- 状态中建议记录：
  - `current_stage`
  - `current_anchor_project_id`
  - `current_competency_id`
  - `competency_states`
  - `authenticity_risk`
  - `cognitive_load`
- `competency_states` 中每个能力项再挂 `evidence_slots`。
- 这样系统才能按证据缺口驱动转场与追问。

## 12. 动态调度逻辑

- 建议新增 `FollowupSelector` 作为统一调度器。
- 调度优先级建议为：
  1. 风控拦截
  2. 当前题证据满足转场
  3. 高真实性风险优先 `ownership_probe`
  4. 关键证据缺失优先追问
  5. 候选人吃力时 `fallback`
  6. 阶段目标完成后切下一阶段
- 最大追问数仍建议保留，但不再作为唯一结束条件。
- 理想状态应优先依据 `evidence_satisfied` 转场，而不是简单“追两次就结束”。

## 13. Prompt 输入升级建议

- 现有 `prompt_builder` 主要输入：
  - `stage`
  - `current_question`
  - `expected_signal`
  - `next_question`
  - `history`
- v2 建议增加：
  - `role_family`
  - `active_competency`
  - `target_evidence`
  - `missing_evidence`
  - `followup_axis`
  - `authenticity_risk`
- 模型应知道当前不是泛泛继续追问，而是在岗位化能力模型下沿某个证据轴继续推进。

## 14. 配置化岗位策略示例

- 建议使用 `YAML/JSON` 维护岗位策略，每个 `role_family` 一份配置。
- 配置中至少应包含：
  - `stage_weights`
  - `competencies`
  - `followup_policy`
  - `question_policy`
- 新增岗位时优先增加配置与模板，不直接修改主引擎。
- 这将避免 `ai_interviews.py` 持续膨胀为岗位分支垃圾桶。

## 15. 与现有代码的迁移映射

### 15.1 `ai_interviews.py`

- 继续作为 facade，对外接口尽量不变。
- `_build_questions`、`_build_questions_with_llm`、`_merge_question_candidates` 逐步迁到 `InterviewPlanner`。
- `_build_followup_question` 保留为兜底规则追问。
- `_build_followup_question_with_llm` 改为接收：
  - `FollowupDecision`
  - `target_evidence`
  - `followup_axis`

### 15.2 `question_flow.py`

- 保留为轻量状态机。
- 继续负责：
  - `active_question_index`
  - `followup_count_current`
  - `question_statuses`
- 不再承担岗位策略决策。

### 15.3 `stage_progress.py`

- 升级为 `EvidenceEngine` 的规则子模块。
- 从只跟踪 `S2/S3` 扩展为多 `competency evidence extractor`。

### 15.4 `flow_policy.py`

- 保留为通用阶段策略。
- 岗位差异通过 `role_profile` 覆盖。

### 15.5 `prompt_builder.py`

- 增加岗位化和证据化输入字段。

## 16. 建议新增的数据结构

- `RoleProfile`：岗位画像，含 `competencies`、`stage_weights`、`followup_policy`、`question_policy`
- `CompetencySpec`：能力项定义，含 `weight`、`priority`、`required_evidence`
- `InterviewPlan`：本场面试的计划结构
- `PlannedQuestion`：题目结构，增加 `competency_id`、`target_evidence`、`followup_axes`
- `InterviewEvidenceState`：运行态证据状态
- `FollowupDecision`：调度器输出，指示 `followup`、`transition`、`fallback`、`handoff`、`close`

## 17. 实施阶段建议

### Phase 1

- 引入 `role_family` 和岗位配置
- 把 `stage quota` 和 `seed question` 先做岗位化

### Phase 2

- 升级题目 schema，增加：
  - `competency_id`
  - `target_evidence`
  - `followup_axes`
  - `red_flags`
  - `satisfaction_rule`

### Phase 3

- 引入 `EvidenceState` 和 `EvidenceEngine`
- 开始按证据更新状态

### Phase 4

- 引入 `FollowupSelector`
- 让转场和追问由证据缺口驱动

### Phase 5

- 报告升级
- 按能力证据输出而不是按题目列表输出

## 18. 首批优先落地范围

- 建议先支持：
  - `backend_engineer`
  - `frontend_engineer`
  - `ai_application_engineer`
- 这是差异最明显、最容易验证 v2 有效性的三类。
- 等三类跑稳后，再扩到：
  - `qa_engineer`
  - `sre_devops_platform`
  - `fullstack_engineer`

## 19. 风险与控制

- 风险一：体系过大，一次性改造成本高  
  控制方法：按 Phase 分阶段迁移，保留旧链路 fallback。

- 风险二：策略配置复杂度上升  
  控制方法：先统一 schema，限制岗位配置字段数量。

- 风险三：LLM 追问不稳定  
  控制方法：先让 `FollowupSelector` 决定追问轴，再交给模型生成自然语言。

- 风险四：评分失真  
  控制方法：先以 `evidence coverage` 为主，避免一开始做过度复杂的综合评分。

## 20. 最终结论

- v2 的核心不是“不同岗位不同题库”，而是“不同岗位不同能力模型与证据目标，统一引擎动态调度题目、追问和转场”。
- 这套方案最适合你们当前代码的原因，是它不要求推翻现有阶段体系、`question_pack` 和 orchestrator，而是逐步把它们升级成岗位驱动和证据驱动。
- 建议从 `role_family + RoleProfile + InterviewPlan` 三件事开始，这是投入最小但收益最大的第一步。
